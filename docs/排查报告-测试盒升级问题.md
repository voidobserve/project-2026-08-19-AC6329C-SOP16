# 排查报告：蓝牙测试盒无线升级的两个问题

- 日期：2026-11-16（2026-11-16 更新：已实施灯数固定修复，见第 6 节）
- 对象：MT2100（AC6329C-SOP16），工程 `project-2026-08-19-AC6329C-SOP16`
- 范围：排查 + 修复问题 2（灯数），问题 1（测试盒连不上）给出检查清单

---

## 0. 结论摘要

| 编号 | 现象 | 结论 | 置信度 |
| --- | --- | --- | --- |
| 问题 1 | 测试盒无线升级时“连接不上” | 与灯的问题**不是同一个根因**，属测试盒侧配置/匹配问题（蓝牙名、上位机选项、KEY、BT_UPDATA 残留），见 4 节清单 | 中（需现场逐条验证） |
| 问题 2 | 升级成功后最长那路幻彩灯**最后 2 颗不亮**，USB 整片下载后又正常 | **根因已定位**：升级保留 VM（用户配置区），旧固件存在 VM 里的 `led_num=113`（28+84+1）覆盖了新固件的 115（30+84+1），WS2812FX/NeoPixel 的 `numLEDs` 被设成 113，第 113、114 号像素的写操作被库直接丢弃 → 末尾 2 颗永远黑 | **高** |
| 问题 3 | “会不会是有缓冲区没加字节对齐” | **不是对齐问题**，见 3 节 | 高 |

问题 2 的三个现象全部能对上：

1. 少了**刚好 2 颗** = 短的那路从 28 改成 30 的差值（`7f73a27`）；
2. 灭的一定是**最长那段（84 颗）的最后 2 颗** = 全局像素号 113、114（段 2 占 31~114）；
3. **只有 OTA 升级后出现，USB 下载后正常** = USB 下载带 `-format all`（擦掉 VM 区），OTA 升级按 SDK 配置**保留 VM 区**。

## 1. 问题 2 的证据链（逐环可查）

### 1.1 VM 区在升级时被保留

`apps/spp_and_le/config/lib_update_config.c:19-20`

```c
//是否支持升级之后保留vm数据
const int support_vm_data_keep = 1;
```

`apps/spp_and_le/board/bd19/board_ac632n_demo_global_build_cfg.h:92-98`（生成 isd_config.ini 用）

```c
#define CONFIG_VM_LEAST_SIZE   8K
#define CONFIG_VM_OPT          2   //config whether erased this area when do a update,1-No Operation,0-Erase
#define CONFIG_BTIF_OPT        1
```

`cpu/bd19/tools/isd_config.ini:86-91`（由上面的宏生成）

```ini
VM_ADR = 0x3D000;  VM_LEN = 8K;  VM_OPT = 2;
BTIF_ADR = 0x3F000; BTIF_LEN = 0x1000; BTIF_OPT = 1;
```

VM 是**独立于代码区的 8K 保留区**，无线升级流程不动它；只有整片下载（`-format all`）才整片擦除：

`cpu/bd19/tools/download/data_trans/download.bat:12`

```bat
isd_download.exe ... -app app.bin cfg_tool.bin -res p11_code.bin -uboot_compress -format all -key 193-AC690X-B718.key
```

> 这解释了“USB 升级方式功能恢复正常”：不是固件不同，而是 USB 那条路把 VM 擦干净了，设备走了“第一次上电”分支。

### 1.2 上电时整块覆盖 `fc_effect`

`apps/user_app/save_flash/save_flash.c:25-54`

```c
res = syscfg_read(CFG_USER_LED_LEDGTH_DATA, (u8 *)(&save_flash3), sizeof(save_flash_t));

if (save_flash3.header != HEADER_VALUE)   // 第一次上电
{
    fc_data_init();                       // 这里才会用编译期常量重新算灯数
    ...
}
else
{
    memcpy((u8*)(&fc_effect), (u8*)(&save_flash3.fc_save), sizeof(fc_effect_t));  // 整块覆盖
    ...
}
```

`fc_effect_t` 里包含 `led_num`（灯点数）和 `led_num_max`（灯点数上限）：
`apps/user_app/led_strip/led_strand_effect.h:125`、`:150`

而 `HEADER_VALUE` 自 2026-08-18 建库以来一直是 `0xAA`，从未按注释要求随版本变更：

`apps/user_app/save_flash/save_flash.h:13`

```c
#define HEADER_VALUE (0xAA)  // 每次更新软件时应修改这个，让升级后第一次清空除遥控外的记忆
```

> `git log -- apps/user_app/save_flash/save_flash.h` 只有建库那一次提交，`0xAA` 从未改过。
> 也就是说 08-18(28 颗) → 11-09(30 颗) 两次发布之间，VM 的“有效性”判据没有变化，旧配置被当成合法数据继续使用。

结果：升级后 `fc_effect.led_num = led_num_max = 1+28+84 = 113`，而新固件编译期是 `1+30+84 = 115`
（`led_strand_effect.c:92-93`）。

### 1.3 灯数直接决定 `numLEDs`，越界写被静默丢弃

`apps/spp_and_le/app_main.c:349,356`（顺序很关键）

```c
read_flash_device_status_init();   // 先从 VM 恢复（含 113）
...
full_color_init();                 // 再用 113 初始化灯带
```

`apps/user_app/led_strip/led_strand_effect.c:158` → `apps/user_app/ws2812-fx-lib/WS2812FX_C/ws2812fx2.c:71`
→ `apps/user_app/ws2812-fx-lib/Adafruit_NeoPixel_C/neo_pixel.c:42-56`

```c
numBytes = pixel_num * 3;      // 113*3 = 339
memset(pixels, 0, numBytes);
numLEDs  = pixel_num;          // 113
```

而写像素时有无条件保护：`neo_pixel.c:275`（`setPixelColor_rgbw`）、`:243`（`setPixelColor_rgb`）

```c
if(n < numLEDs) {   // n = 113/114 时直接 return，不报错、不写入
```

段范围是**编译期常量**，不随 VM 变：`led_strand_effect.c:318-347`

```
SEG0 = 0        (1 颗，七彩灯)
SEG1 = 1..30    (30 颗，短的那路)
SEG2 = 31..114  (84 颗，最长那路)   ← 113、114 属于这里
```

所以效果照常往 31~114 写，但 113、114 两次写入被库挡掉，这两颗的 `pixels[]` 永远是 0 →
`ledc_send_rgbbuf_isr(1, ..., 84, 0)` 照样把 84 颗的数据全发出去（`ws2812_drive.c:171`），
只是后两颗发的是全 0 → **不亮**。

`set_ls_lenght()` 也救不回来：它按 `led_num_max`（同样被恢复成 113）钳位
（`led_strand_effect.c:1472-1474`），涂鸦 App 下发 115 也会被压回 113。

### 1.4 为什么“最后两颗”而不是别的

短边 30 颗带来的差值正好是 2；段 2 是最后一段，所以缺的正好落在整条灯带的物理末端。若当初改的是中间段，会得到“中间某段末尾灭”的对称现象。

## 2. 与上一版修复的关系（避免重复归因）

`92fd444`（11-12）修的是 **效果函数内部** 的段尾下标（`close_effect` 多减 1 导致第 84 颗常暗、`open_effect`、像素寻址、音乐效果漏灯等）。那是“效果算法漏掉某颗灯”，与本次的“库层面 numLEDs 挡住末尾两颗”是**两个独立缺陷**，可以叠加：

- 若只在**个别模式**下末尾灭 → 效果算法问题（`92fd444` 那一类）；
- 若在**所有模式**下末尾 2 颗都灭 → 就是本次的 `led_num` 问题。

报告末尾的验证步骤 2 就是用来区分这两类的。

## 3. 排除“缓冲区没加字节对齐”

用户怀疑的方向可以排除，依据：

1. 两路缓冲区都显式 4 字节对齐，并且单独放在自定义段里：
   `apps/user_app/ws2812-fx-lib/WS2812FX_C/ws2812_drive.c:15-19`
   ```c
   #define WS2812_LED_BUF_SEC  __attribute__((section(".ws2812_led_buf"), aligned(4)))
   static u8 led_val_buf1[huancai1_num] WS2812_LED_BUF_SEC;   // 90
   static u8 led_val_buf2[huancai2_num] WS2812_LED_BUF_SEC;   // 252
   ```
2. 该段在链接脚本里被显式收进 `ram0` 的 `.bss`，前后 4 字节对齐，并额外保留 ≥0x1000 字节空间：
   `cpu/bd19/sdk_ld.c:316-323`
3. 库的像素缓冲同样对齐：`neo_pixel.c:34` `static uint8_t pixels[3000] __attribute__((aligned(4)));`
4. LEDC 是按 **bit 数** 取数据的（`cpu/bd19/ledc.c:117` `FD = led_num*3*8`），不是按字长；252、90 字节都不是问题（第 90/252 字节后可能被多读 2 字节，但落在本段内，无害）。
5. **反证**：对齐问题若成立，现象应是整条灯带偏色/闪烁/尾部随机乱码，且 USB 下载后同样出现——与“固定末尾 2 颗、只在 OTA 后出现”不符。

顺带说明：`Disp_buf_Len 1100`（`led_strip_sys.h:56`）和 `pixels[3000]` 对 115 颗都够用（115*3=345），不存在溢出。

## 4. 问题 1：“测试盒连接不上”的排查清单

这一条**没有本地代码证据可闭环**（需要现场硬件），以下按可能性排序，均来自杰理官方文档：

官方 FAQ（<https://doc.zh-jieli.com/Tools/zh-cn/mass_prod_tools/testbox_1tuo2/tb_common_problem.html>）原文：

> **1. 测试盒连接过程中能显示连接地址，但一直连接不上待连设备，无法进入测试或升级？**
> 可能原因：测试盒在 PC 配置界面使能了“升级电量门限”“SDK信息”“电量及校验码”等需要 SDK 同步支持的配置项，但待连设备的固件未支持这些功能。
> 解决方法：在 PC 配置界面关闭这几项新功能的使能开关，或者直接点击“加载默认设置”加载出厂配置，保存复位再进行测试。

### 4.1 按优先级逐条核对

| # | 检查项 | 依据 / 做法 |
| --- | --- | --- |
| 1 | 关闭测试盒上位机中“升级电量门限 / SDK信息 / 电量及校验码”，或“加载默认设置”后保存+重启测试盒 | 官方 FAQ 第 1 条，症状描述与本问题完全一致（能显示地址、连不上） |
| 2 | **蓝牙名必须与测试盒配置的“固定连接设备名字”完全一致** | 无线升级按名字搜索样机（<https://doc.zh-jieli.com/Tools/zh-cn/mass_prod_tools/testbox_1tuo2/tb_wireless_upgrade.html>、`tb_view_bt_info.html`）。本项目 08-18 记录“修改了蓝牙名称”，若产线测试盒里填的还是旧名字，就会出现“搜到地址但连不上”。用手机/PC 蓝牙扫描核对设备名 |
| 3 | **KEY 一致性** | 官方：`AC690x_sdk_211` 以上版本支持“key 不同不进行升级”，会报错。本工程 `download/data_trans/download.bat:12-13` 当前用 `193-AC690X-B718.key`（旧 KEY），`XYH-AC690X-D00C.key` 被注释；开发记录 08-19 提到“用新 KEY 生成软件”、08-29 又改回旧 KEY。请确认：给测试盒的固件与现场设备是**同一个 KEY** 生成的 |
| 4 | 设备是否处于“待重升”状态 | 官方：升级中断后样机的蓝牙名会变成 `BT_UPDATA`，需重新升级；此时按原名字搜索不到，表现为“连不上” |
| 5 | 给测试盒的文件类型 | 无线升级用的是 **`.ufw` / `.bfu`**（本项目为 `cpu/bd19/tools/download/data_trans/` 下的 `update.ufw`，即 `code\update.ufw`），不是 `jl_isd.fw`。TF 卡里放 `.fw` 会用不了 |
| 6 | 其它 | 设备数量/距离/干扰；“升级电量门限”导致低电拒绝；测试盒固件版本过低（`isd_config.ini:113` 要求 `1TO2_MIN_VER = 2.27.8`）；若用 ufw 校验码匹配功能，`目标校验码配置` 必须填当前 ufw 的校验码（<https://doc.zh-jieli.com/Tools/zh-cn/mass_prod_tools/testbox_1tuo2/tb_ufw_crc_compare.html>） |

### 4.2 一个和问题 2 同源的隐患（值得一起注意）

BTIF 区（蓝牙名/地址，`0x3F000`）在升级时同样**被保留**（`BTIF_OPT = 1`）。所以：

- 用 **OTA/测试盒** 升级，设备**不会**改名；只有 **USB 整片下载**（能重写 BTIF）才会变成工程里配置的新名字。
- 如果现场设备是旧名字、而测试盒/产线按新名字去搜，就会“USB 能升、无线升不了、也连不上”。

这与“灯不亮”是同一类根因：**升级保留的保留区（VM / BTIF）与新版固件配置不一致**。

## 5. 验证步骤（现场 3 步，不需要改代码）

1. 找一台“测试盒升级后末尾 2 颗不亮”的设备（**旧固件**），用涂鸦 App 连接，读“灯带长度”（DP `0x0408`，`dp_data_tran.c:280-285`）：
   - 显示 **113** → 本报告结论成立（旧配置残留）；
   - 显示 **115** → 本次结论不成立，需回到效果代码继续查（转 2 节）。
   > 本报告 6 节的修复已实施，打上新固件后该值恒为 115（`FC_LED_NUM_MAX`），此步骤只用于复盘旧固件。
2. 在同一台设备上切换几个不同类型的效果（静态 / 音乐律动 / 跑马 / 流星）：
   - **所有模式**末尾 2 颗都灭 → 库层 `numLEDs` 问题（本报告）；
   - 只有个别模式灭 → 效果算法越界问题（`92fd444` 那一类，需按模式逐个看）。
3. 用 USB 整片下载同一份固件（`-format all`）后再看 → 恢复正常（用户已观察到），闭环确认“VM 残留”假设。

## 6. 已实施的修改（2026-11-16）

方案：**灯带长度不再跟随 VM，上电时按当前固件的物理灯数固定**（采用用户提出的“最后固定住灯的数量”）。

### 6.1 改动清单

| 文件 | 改动 |
| --- | --- |
| `apps/user_app/led_strip/led_strand_effect.c` | 新增 `FC_LED_NUM_MAX`（= 段0+段1+段2，编译期常量）；`fc_data_init()` 改用它；新增 `fc_led_num_fix()` |
| `apps/user_app/led_strip/led_strand_effect.h` | 声明 `fc_led_num_fix()` |
| `apps/user_app/save_flash/save_flash.c` | `read_flash_device_status_init()` 末尾调用 `fc_led_num_fix()`（两个分支之后，即 VM 恢复之后） |

```c
/* led_strand_effect.c */
#define FC_LED_NUM_MAX      (USER_WS2812_SEGMENT_0_LEN + USER_WS2812_SEGMENT_1_LEN + USER_WS2812_SEGMENT_2_LEN)

void fc_led_num_fix(void)
{
    fc_effect.led_num_max = FC_LED_NUM_MAX;
    fc_effect.led_num = FC_LED_NUM_MAX;
}

/* save_flash.c：read_flash_device_status_init() 末尾 */
fc_led_num_fix();
```

### 6.2 为什么这样改

- **单点修正**：所有会影响灯数的入口只有三处——`fc_data_init()`（首次上电）、VM 恢复（升级后）、`set_ls_lenght()`（该函数无调用者）。在 VM 恢复函数末尾固定一次，`my_main()` 里随后的 `full_color_init() → WS2812FX_init()`（`app_main.c:349/356`）拿到的必然是 115。
- **不再有第二处公式**：原来 `fc_data_init()` 和 `save_flash.c` 各写一遍 `1 + SEG1 + SEG2`，改灯数时容易漏改一处（这次的 bug 就是“两处来源不一致”的同类问题）。现在统一走 `FC_LED_NUM_MAX`。
- **为什么是“固定”而不是“只压上界”**：本产品灯带长度固定；`led_num` 虽然能被涂鸦 DP `DPID_LED_NUMBER_SET` 改写（`dp_data_tran.c:184-203`），但该 DP 只改数值、不会重新 `WS2812FX_init()`，所以不会造成末尾变暗；反过来说，让 VM 里的旧值参与初始化没有任何收益，固定住最省事也最直观。
- **没有改 `HEADER_VALUE`**：不需要。固定灯数后，旧 VM 里的 `led_num=113` 不会再被用于初始化，其他用户状态（亮度/模式/RGB 顺序）本来就该保留，强制清一次反而丢用户设置。若以后 `fc_effect_t` 结构体字段有增删，**必须**改 `HEADER_VALUE`（`save_flash.h:13`），否则 `memcpy` 会错位。

### 6.3 顺带确认（未改，仅记录）

1. `save_flash_t` 目前没有版本/长度字段，`fc_effect_t` 一改字段就会错位——以后动结构体时记得改 `HEADER_VALUE`。
2. `syscfg_read()` 的返回值 `res` 仍未校验（`save_flash.c`），读到短数据也只能靠 header 兜底。
3. `ble_state = 1;` 紧接着被 `= save_flash3.ble_state`（0）覆盖，且该变量无其他读者，属无效代码。
4. `set_ls_lenght()`（`led_strand_effect.c:1490`）目前无调用者；若以后启用，它会把 `led_num` 设小并重新 `WS2812FX_init()`，那才会再次出现“末尾不亮”，届时需一并改成固定值。

> 本次改动**未编译**（遵 `.agents/.agents.md`），需在本地 `make` + 实机验证。
